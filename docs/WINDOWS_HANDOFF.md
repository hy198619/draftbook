# DraftBook（草稿本）Windows 版开发交接

> 记录于 2026-10-12。基线是 GitHub 仓库 `hy198619/draftbook` 的 `main` / `v0.9.6`（提交 `a728753`）。这是新开发对话的入口，不代替实际代码；开始工作前先核对 `git status`、版本和相关实现。

## 产品定位与必须延续的体验

DraftBook 是给一人公司主理人和内容创作者的轻量草稿本，是文字的临时中转站，不是需要不断整理的知识库。典型内容包括灵感、视频笔记、待发送的消息或邮件、临时待办、稍后会用的网址或账号名。界面应适合收窄后常驻屏幕一侧，打开即可写，不必先建文件、标签页或标题；正文以纯文本为基础，复制时保留原始文字和 Markdown 语法。

- 顶部始终是新草稿输入区；写完一条，用明确的键盘快捷键划定为独立草稿。macOS 为 `⌘+Enter`；Windows 快捷键应按平台习惯设计并在界面中说明，不能原样显示 Mac 键位。
- 不同草稿在同一页纵向排列，由应用内部的分隔结构区分；分隔线不是正文，不能被选中或复制。草稿独立编辑、复制、固定、分类、存档或删除；正文长时完整展开，不做固定高度的内部滚动框。
- 草稿自动保存，重启后恢复未划定输入和已划定草稿。中文输入法正在组词／选候选时不得重建编辑器、回写旧文本或“吞字”；这一点在 macOS 0.9.3 曾是实际缺陷，Windows 必须专项测试。
- 划定后的 Markdown 自动预览，无需手动开关；编辑时保留源码和换行，复制整条时复制原始语法。当前 macOS 使用 Swift Markdown 解析 CommonMark 与常用 GFM 扩展。普通点击链接进入编辑；组合键点击可打开网页或现有本地文件，危险目标需要确认。Windows 组合键可按平台习惯确定。
- 黑色标签固定为“未分类”，五种彩色标签默认叫“分类1”至“分类5”，可自定义名称；按标签筛选草稿及存档。标签颜色按**创建时间**在未满 5 天、满 5 天、满 7 天、满 30 天四档降低饱和度；清理周期另按**最后编辑时间**计算，两者不能混淆。
- 到期草稿保留独立“待处理／清理台”入口，可延期、固定、存档或删除。存档草稿仍可编辑标题、正文和标签；删除后进入可恢复的回收站。支持全文搜索、TXT／Markdown 导出、完整 JSON 备份与恢复，以及自动备份。
- 本地优先，不要求账号，不上传草稿；现有数据未加密，不能宣传为密码管理器。更新检查只有用户主动触发时才联网。Windows 版的更新与安装流程需另行设计，不照搬 macOS DMG。

## 现有仓库与数据契约

- `Sources/DraftBook/` 是 macOS 的 SwiftUI/AppKit 界面、文本编辑器、Markdown 预览、链接打开、菜单与更新检查；`Sources/DraftBookCore/` 包含 `Draft`、`DraftStore`、`DraftTiming`。`DraftStore` 依赖 Combine／`ObservableObject`，不能假定整个 Swift 包可在 Windows 直接编译；可复用的是行为、模型定义和测试用例，技术复用须实际验证。
- `Package.swift` 目前只声明 macOS 14；`README.md` 是产品与功能概览，`CHANGELOG.md` 记录已发布行为，`RELEASE.md` 是 macOS 打包流程，`Tests/` 有核心逻辑与编辑器测试。现有公开版为 0.9.6 Public Beta。
- macOS 主数据位于用户目录下的 `com.yangyuxuan.DraftBook/drafts.json`，完整备份也是 JSON。当前快照 `schemaVersion = 5`，顶层字段为 `schemaVersion`、`composer`、`drafts`、`labelNames`；日期用 ISO 8601，草稿模型和可缺省字段见 `Sources/DraftBookCore/Draft.swift`。如做跨平台导入，应使用**合成测试数据**建立兼容测试，不读写用户真实草稿，也不要假定 Windows 与 macOS 共用同一数据目录。
- 仓库采用 PolyForm Perimeter License 1.0.1，是 Source Available，不是 OSI 开源许可；Windows 新代码及依赖的发布方式要与此兼容。不要把个人资料、真实草稿、令牌或设备路径写入公开文件。

## Windows 开发的待决事项与建议顺序

1. 先调查当前可用的 Windows 开发／运行环境，比较适合常驻、轻量、可靠中文输入、富文本预览和安装分发的技术方案；明确哪些逻辑可共享、哪些必须重写。不要未经评估就选框架，也不要为了跨平台统一而牺牲本产品最核心的输入体验。
2. 给出 Windows 第一阶段的最小可试用闭环：单窗口输入、划定、自动保存与重启恢复、草稿编辑／复制，以及与 macOS 版一致的基础数据模型。随后再补分类、Markdown、清理台、存档、回收站、备份、更新等能力；如果打算改变顺序，先说明依据。
3. 保护现有 macOS 版：Windows 代码和测试应清晰隔离；不得修改或发布现有 0.9.6 Release。数据格式若要演进，先设计向后兼容和失败恢复，再改代码。公开发布 Windows 安装包前另行取得用户明确确认。
4. 验收须包括 Windows 真机／虚拟机上的中文输入法、长文本、自动保存与重启、窄窗口布局、链接安全、安装卸载和内存占用。若当前只有 macOS 环境，可以完成可验证的设计、共享规格与代码，但不能声称 Windows 实机体验已通过。

需要向用户确认、不能自行假定的产品选择：Windows 是否与 macOS 功能完全同版同步，首个测试版接受哪些功能暂缓；是否要求读取 macOS 完整备份；最低 Windows 版本及安装分发目标。没有这些答案时，可先做不依赖选择的技术核查和最小原型。
